审查前先读取 `review-discipline.md`，遵循其中定义的审查纪律。

## 审查内容

### 静态扫描

- 探测 `mcp__idea-mcp` 的连通性，不通则跳过本步骤。
- 对每个变更文件调用 `mcp__idea-mcp__get_file_problems(errorsOnly=false)`，获取全量诊断信息。
- 按变更行号过滤，仅保留变更行上的诊断项。

### 通用审查

对变更代码进行以下维度审查。每个维度附引导性问题，帮助判断是否存在真实问题：

**代码结构**

- 职责单一：一个代码单元是否处理了多个不相关的关注点？描述其行为时是否需要"和"字？
- 抽象层次：同一方法内是否混杂了不同抽象层级的操作（如业务流程编排中直接拼接 SQL）？
- 重复逻辑：是否存在相同意图的重复代码——不只是文本相似，而是"改一处是否需要同步改另一处"？

**错误处理**

- 异常吞没：catch 块是否仅记录日志而不重新抛出，导致调用方对失败无感知？
- 异常粒度：是否捕获了过于宽泛的异常（如 `catch(Exception)`），掩盖了意料之外的错误？
- 失败一致性：异常发生后，数据状态、外部资源、业务状态是否仍保持一致？失败操作是否可安全重试？
- 事务边界：多步操作的部分失败是否会导致数据不一致？事务范围是否过宽或过窄？隔离级别是否匹配业务？涉及多个数据源时是否有补偿机制？

**架构与设计**

- 依赖方向：高层策略是否直接依赖了低层实现细节？抽象是否依赖了具体？
- 扩展方式：新增行为是通过扩展点实现，还是通过修改现有代码（if-else 分支膨胀）？
- 变更影响面：修改一个功能点，是否需要在多处做配套修改？

**边界条件**

- Null/空值：返回值、集合、参数是否可能为 null 或空？下游代码是否对此有防御？
- 数值安全：是否存在除零、溢出、符号反转、浮点直接比较等风险？
- 字符串边界：是否处理了空字符串、仅空白、超长输入、特殊分隔符？
- 并发安全：共享可变状态是否有同步保护？"检查后操作"（TOCTOU）是否原子？

**性能隐患**

- 重复计算：热路径中是否存在每次调用都重复执行、但结果可缓存或可提前计算的操作？
- 数据访问：是否存在 N+1 查询模式、无分页的全量获取、无界集合累积？
- 资源持有：外部资源（连接、流、锁）是否必然释放？大对象是否被无意长期持有？

**代码异味**

- 死代码：注释掉的代码块、从未执行的分支、只写不读的变量
- 硬编码假设：依赖特定环境值（端口、路径、超时）但未显式声明，修改时极易遗漏
- 复杂度集中：单个方法承担过多决策分支——深层嵌套、长串 if-else 可考虑提前返回或策略表

### 排除项

以下情况直接跳过：

- "考虑添加错误处理" — 异常已被调用方或框架处理时
- "缺少输入校验" — 方法为内部方法且调用方已验证时
- "魔法数字" — 已知常量（200、404、1000ms）或语义自明的局部常量
- "函数过长" — 穷举 switch、配置对象、测试数据表
- "硬编码值" — 测试固件、示例代码
- "可能空指针" — 前一行已有类型收窄或 if 守卫

## 严重程度定义

| 级别 | 图标 | 标准 |
|------|------|------|
| 严重 | 🔴 | 会导致数据丢失/损坏、服务崩溃、死锁、资源耗尽 |
| 高危 | 🟠 | 存在明确缺陷，特定条件下触发功能错误或异常 |
| 中危 | 🟡 | 偏离最佳实践，降低可维护性或存在潜在风险 |
| 建议 | 🔵 | 风格、命名等表层问题，不影响正确性 |
